## 罠と袋小路
- fp16 attention over 4,096 keys or more: one fp16 sum over 8,192 keys lost 18 % in the Gaussian decoder's first block; summing the attention-weights × values product over centred 1,024-key chunks loses 0.6 % (exact in real arithmetic, since each softmax row sums to 1). Registry row `mldrift-fp16-long-key-attention-sum`.
- BiRefNet's deformable convolutions as a gather with bilinear weights + one matmul: same arithmetic (5.5e-6 from the author's map), but the LiteRT GPU has no kernel for the gather, so BiRefNet runs on the CPU; the CPU runtime ran every row tile's gather before using any (first export: out of memory on the S26) until each tile's offsets waited on the previous tile's output. One call still peaks at VmHWM 3.96 GiB. Registry row `litert-cpu-lookup-before-consumer`.
- One REDUCE_MAX over a whole 1024 × 1024 map (the VAE GroupNorm scale) took 8 s per S26 GPU call; a max pool then a max over the 32 × 32 result takes 0.83 s. Registry row `adreno-reduce-max-whole-map`.
- Long S26 GPU calls: the VAE encoder as one graph (about 9 s per call) stalled the compositor and the process was killed (signal 9) on its fifth call; every stage is split (calls 0.045–1.83 s). Registry row `idol-s26-gpu-call-length`.
- The Pixel 11 Pro (PowerVR) returns GPU memory seconds after a close: the pool's eviction loop read MemAvailable too early (NotEnoughMemory at 1,758 vs 1,768 MB) → wait after each eviction (`awaitAvailable`; free on the S26: median gap 0.001 s over 109 closes).
- S26 thermals: the GPU clock cap falls 1,300 → 422 MHz within one photo even from a cool phone; `dumpsys thermalservice` "Cached temperatures" is stale (read "Current temperatures from HAL" and "Thermal Status"); a phone kept charging with the screen on settles at status 1 (skin 38.5 °C), never 0.
- The sample's viewer was never run on a device before day-0 and failed there (no usable Content-Length in the WebView) — a sample's success path includes its last screen; record it before the card says "sample".
- The pool's estimate for the CPU graph (file size + 26 × the largest tensor) misses BiRefNet's run peak; with another app resident the system killed the run during background removal.
