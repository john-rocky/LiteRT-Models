# SAM 3.1 (facebook/sam3.1) — LiteRT CompiledModel GPU precheck (2026-08-19)

**Verdict: 画像側を先に出せる / tracker は第 2 段.**
The image side (ViT-L/14 @1008 → tri-neck → text-prompted DETR head → masks) exports,
lowers, and — after the exact 4-D re-authoring in `scripts/vit4d.py` — the vision graph
runs **fully accelerated on the host-Mac GPU** with detection-level parity to PyTorch.
The Object-Multiplex tracker is a clean second stage: it *shares the same ViT trunk*
(3 neck heads on one trunk) and its per-frame step is four fixed-shape sub-graphs plus
~3k lines of host orchestration, i.e. the SAM2 video-port pattern, but with a bucket
(16 objects) dimension and an 8-head memory attention over 5184 tokens.

Everything below was measured in this session on an M4 Max (128 GB), `sam3/.venv`
(torch 2.12.1 CPU/MPS, litert-torch 0.9.3, ai-edge-litert 2.1.6 with the Metal
accelerator), checkpoint `sam3.1_multiplex.pt` (3.50 GB, gated, downloaded with
aria2c ×16 ≈ 7 min at ~8 MB/s).

Total fp16 on device ≈ 1.73 GB (vision 930 + text 707 + head 97). Vision is under the
sub-1 GB single-graph Mali threshold, but only just.

**Block-level diagnosis of the raw-vision failure** (`scripts/diag_vit_blocks.py`):
patch-embed + tiled pos-embed exact (corr 1.0), one window block corr 0.995 / max 4.4, one
global block corr 0.806 / max 8.6 → the mis-lowering is inside the attention path
(5-D qkv permute + interleaved-RoPE strided slices/stack), not the pos-embed. It is a
converter-side correctness bug on >4-D graphs (worth a litert-torch repro later), and
irrelevant once the graph is 4-D.

**`scripts/vit4d.py` (exact, verified corr 1.000000 / max|diff| 2.5e-4 vs stock in torch):**
- tiled 24²→72² abs-pos baked as a constant buffer;
- qkv sliced along channels, heads by 4-D reshape+transpose;
- interleaved RoPE de-interleaved by permuting the Q/K rows of the qkv weight (same
  permutation on q and k ⇒ q·k unchanged) → half-split rotation on 4-D tensors
  (recipe `[[reference_interleaved_rope_bake]]`);
- explicit matmul + softmax attention;
- exact ≤4-D window partition: reshape → transpose → reshape → **transpose** (the SAM2
  order-swap trick is NOT valid here — RoPE is position dependent inside the window — the
  extra transpose restores the exact layout);
- SafeLayerNorm (scale-before-square, 1/32) on ln_pre / norm1 / norm2 (see §3).

Vision graph, M4 Max, single image (1008²):

| runtime | time / image | parity vs torch fp32 (features) |
|---|---:|---|
| torch fp32 CPU | 2.8 s | — |
| torch fp32 MPS | 0.96 s | — |
| tflite XNNPACK CPU (fp32 file) | 2.6 s | corr 1.00000, max 1.9e-4 |
| **CompiledModel GPU (Metal), fp16 default** | **526 ms** (compile 5–7 s, `is_fully_accelerated=True`) | corr 0.994, rel-rms 5–6 %, max\|diff\| ~2–4 |
| **CompiledModel GPU (Metal), `GpuOptions.enforce_f32=True`** | **711–724 ms**, fully accelerated | **corr 1.000000, rel-rms 8e-4, max\|diff\| 0.1** |

Head (torch): CPU 0.31–0.65 s, MPS 0.46 s; tflite CPU 398 ms. Text: tflite CPU 26 ms.

The fp16 feature error is the deep-ViT "massive activation" class: the residual stream
grows from |x|≈25 (block 0) to **|x|≈300 (blocks 16–31)** (`scripts/diag_magnitudes.py`).
SafeLayerNorm removes the variance overflow (corr 0.9899 → 0.9943) but the remaining error
is fp16 *storage precision* of a ±300 residual (spacing 0.25) — not an op bug: `enforce_f32`
makes the same graph exact. **Detection-level gate** (`scripts/e2e_gate.py`: GPU vision
features → PyTorch text+head, real images):

| image / prompt | torch fp32 kept | GPU fp16 vision | GPU f32 vision |
|---|---|---|---|
| truck.jpg / "wheel" | 4 (p=0.94/0.94/0.88/0.90, presence 0.99) | same 4; box IoU ≥0.993, **mask IoU ≥0.974 (mean 0.991)**, \|Δp\| ≤0.001 | identical (IoU 1.000) |
| groceries.jpg / "paper bag" | 4 (p≈0.83, presence 0.93) | same 4; box IoU ≥0.9987, mask IoU ≥0.9988, \|Δp\| ≤0.0004 | identical |
| groceries.jpg / "bottle", test_image.jpg / "person" | 0 (presence 0.06 / 0.14) | 0 (presence 0.06 / 0.20) | 0 |

So fp16 (what Mali always computes, and the fast Metal path) is acceptable at the mask
level for this model; f32 is available on Metal (Mac/iPhone) if we want bit-parity.

`litert-lint` (litert-compat) was run on all three graphs against
`gpu_mldrift__2.1.5` and `gpu_metal_mac__2.1.6`: **inconclusive** — those matrix snapshots
hold 1–2 entries each, so every op is reported "unknown / no entry". Residency evidence in
this precheck = `CompiledModel.is_fully_accelerated()==True` on Metal for the vit4d vision
graph + the ML-Drift banned-op check (only TRANSPOSE_CONV ×3 left in vision).

Mobile estimates (not measured — no device in this session): ViT-L @5184 tokens ≈ 5 TFLOP
per image (28 window blocks + 4 global; global attention matrix 16×5184² = 430 M elements
= 860 MB fp16 per block — must be query-chunked for phones). Pixel 8a Mali ≈ many seconds
per image; iPhone 16-class Metal ≈ 2–4 s fp16 from the 526 ms M4 Max figure.

## 4. ③ Tracker (Object Multiplex) step boundary — read-through

Files: `sam3/model/video_tracking_multiplex.py` (`track_step` → `_track_step_aux` →
`_prepare_memory_conditioned_features` → `_forward_sam_heads` → `_encode_new_memory`),
`decoder.py` (`TransformerEncoderDecoupledCrossAttention`, `SimpleRoPEAttention`),
`multiplex_mask_decoder.py`, `memory.py`, `multiplex_utils.py` (`MultiplexState`,
buckets of `multiplex_count=16` objects), host loop in `sam3_multiplex_tracking.py` /
`sam3_multiplex_base.py` (~6.4k lines: detection↔tracklet association, NMS, hotstart,
recondition every 16 frames, masklet confirmation).

Per frame t, per bucket b (16 objects):
1. **backbone**: the SAME ViT-L trunk as the detector (`del tracker_model.backbone`; the
   detector's tri-neck feeds `interactive` + `propagation` heads) — one trunk pass serves
   detection + tracking. Stored per memory frame: `image_features` (5184×256, because
   `save_image_features=True`) + `image_pos_enc`.
2. **memory attention** (`transformer.encoder`, 4 layers, d=256, 8 heads, RoPE 72×72,
   decoupled): queries = current image tokens (5184) expanded per bucket; keys = up to
   `num_maskmem=7` spatial memories (each 72×72×256, one memory per bucket per frame — the
   16 objects are multiplexed into channels by the mask downsampler, `starting_out_chan=4`,
   `input_channel_multiplier=2`) + object pointers (16 objects × up to 16 frames, RoPE
   excluded via `num_k_exclude_rope`) with temporal pos-enc; the image part of q/k is shared
   (`image_cross_attn_{q,k}_proj(image)`) and the object part is per bucket.
   → Fixed-slot export (mask unused slots) exactly like `sam2/scripts/convert_sam2_video.py`
   `memcond{N}`; but 8 heads × 5184 × (7·5184+256) keys ≈ 1.5 G attention elements per
   layer → needs slot-chunked attention on mobile.
3. **multiplex mask decoder** (SAM two-way transformer, 16 object tokens jointly) →
   masks/IoU/obj-ptr/obj-score for the 16 objects (multimask via stability).
4. **memory encoder** (`SimpleMaskEncoder`, out 256) on the 16 masks + pix feats → one
   72×72×256 memory per bucket per frame.
5. **host**: rolling bank (7 spatial + 16 pointer slots), detector run + association every
   frame (`recondition_every_nth_frame=16`), NMS/hotstart/confirmation heuristics.

All four sub-graphs are fixed-shape given (bucket=1 → 16 objects, N=7 slots) — same
export shape as the SAM2 video port, so it is a real but second-stage job (host state
machine is 2–3× SAM2's).

## 5. Env / shims needed to run the OSS code on CPU/MPS (all in `precheck_sam3.py`)

- `sam3.model.edt` imports `triton` unconditionally → stub module (`edt_triton=None`).
- `PositionEmbeddingSine(precompute_resolution=1008)` allocates on `"cuda"` → build with
  lazy cache; `TransformerDecoder._get_coords(device="cuda")` → CPU.
- ViT MLP uses `perflib.fused.addmm_act` (bf16 CUDA fused addmm) → plain `act(linear(x))`.
- `Tensor.pin_memory()` in the geometry encoder → no-op.
- ViT attention keeps a complex64 `freqs_cis` buffer next to the real/imag pair
  (`use_rope_real=True`) → dropped (litert-torch cannot serialize complex).
- Head export: log-RPB `feat_size` arrives as 0-d tensors → pinned to (72,72);
  text-only prompt still calls `roi_align` / `grid_sample` on ZERO boxes/points and
  `concat_padded_sequences` (data-dependent scatter) → empty-safe wrappers (exact).
- torch 2.12.1 needs torchvision 0.27.x (uv resolved 0.28 → `torchvision::nms` missing);
  `PYTORCH_ENABLE_MPS_FALLBACK=1` for `_assert_async` on MPS.

## What was re-authored beyond the precheck (all exact, torch corr 1.0000000)

- **Head**: every MHA (sam3's AND torch's `nn.MultiheadAttention` — the decoder's
  self/ca_text attn are plain torch modules; patching only sam3's left them silently

## Metal-delegate execution bugs found (compiles fine + `is_fully_accelerated=True`, wrong numbers)

Isolated by sub-graph bisection (`diag_text_gpu.py`, `diag_head_gpu.py`); each has a
minimal repro pair in those scripts:

1. **SOFTMAX fed by an elementwise op with a broadcast constant** (additive causal /
   padding mask) mis-executes (block corr 0.43 at depth 24). Fix shipped: masked
   softmax as `m = max(s·keep + (1−keep)·NEG); e = exp((s−m)·keep)·keep` — the
   `clamp`/`min`/`relu` variants of the same math ALSO mis-execute; the `·keep`
   inside exp is the form that works. For additive biases (log-RPB):
   `e = exp((s−m)+bias)`.
2. **Rank-3 `(n,1,C)`/`(1,n,C)` seq-first activations with fan-out** mis-execute
   broadcast elementwise ops (`b_add_out` repro: `(200,1,4) + (1,1)` wrong, same values
   rank-4 exact). Fix shipped: batch-first decoder + rank-4 text encoder. (Mirror of
   the Mali `[1,N,C]` fanout bug — likely the same ML Drift lineage.)
3. **DEQUANTIZE feeding an elementwise op / multi-consumer fp16 constants** refuse to
   compile ("Expected 1 const input tensor(s)"). Fix: fp16-quantize only
   FULLY_CONNECTED/CONV weights (`RECIPE_MATMUL_ONLY`), keep `boxRPB_embed` fp32, and
   emit only the last decoder layer's heads (single-consumer weights).
4. **All-constant op chains** refuse to compile → runtime zero
   (`clamp(x[:1], 0, 0)`) added to constant-rooted tensors (query embeds, ref boxes,
   geometry cls).
5. fp16 execution walls (not bugs): text |x|≈1.2e3 → **corrupts prompts**
   ('window', 'paper bag' lose all detections) → run text on CPU (Android) or
   `enforce_f32` (Metal, 10 ms); GroupNorm big single reduce → hierarchical means;
   head fp16 leaves kept-set intact (mask IoU ≥0.989) but borderline |Δprob| up to 0.15.

**Two device-only walls found and fixed:**
1. **Mali [1,N,C] fanout bug hit the DETR head** ([[reference_mali_3d_sequence_fanout_bug]]
   witness #3): the rank-3 decoder output (1,200,256) fanning out to score/box/mask heads

   XNNPACK fine). Fix: `decoder_forward_bf` returns rank-4 (1,1,200,256) and all three
   heads consume rank-4 (mask einsum -> rank-4 matmul).
2. **LiteRT 2.1.5 mis-executes even the FIXED head graph** (still constant logits), while
   the SAME .tflite on 2.2.0 (com.litertprobe and the app after the bump) is correct.

## iOS Metal runtime wall catalog (evening 2026-08-20, iPhone 17 Pro, CLiteRTLM v0.15.0)

Discovered while bringing the full tracker (7 graphs, ~830M params) up on the iPhone —
every failure silent (no exception, no crash report unless noted), each needed a device
iteration to isolate. In encounter order:

1. **Per-tensor-buffer cap ~112 MiB (0x7000000 B)** for managed host-memory buffers:
   memattn's 117.4 MB input fails creation (status 3) while smaller buffers pass.
   Fix: split the flat input into 2 tensors at export (`export_memattn_2in.py`, 79.6+37.8 MB,
   bit-identical) + multi-input `Sam3Graph` that writes one flat array across inputs in
   signature order (callers unchanged).
2. **Managed tensor-buffer pool ~512 MB total** (any buffer type): with all 7 graphs'
   I/O buffers persistent (~640 MB), creation starts failing around 504 MB cumulative —
   which buffer fails depends on creation order, so it looks nondeterministic.
   Fix: create/destroy I/O buffers per run() call (only one graph's set alive at a time).
3. **GPU-compiled graphs execute ONLY with the buffer type their requirements list**
   (`kLiteRtTensorBufferTypeMetalBufferPacked` = 34): host-memory buffers create and
   compile fine but the RUN fails with status 3 (unlike Android CL, which accepts host
   I/O). Requirements' `BufferSize` equals the f32 linear size; creating type 34 at any
   OTHER size fails with status 9. Lock/Unlock does the layout conversion, so plain f32
   memcpy through the lock is correct.
4. **Default app memory ceiling**: at ~2.4 GB footprint the first vision run's extra
   allocation aborts (`swift_abortAllocationFailure`, SIGABRT — the one failure WITH a
   crash report). Fix: the `com.apple.developer.kernel.increased-memory-limit`
   entitlement — which a wildcard team profile does NOT carry; one Xcode GUI build with
   automatic signing regenerates the profile, after which CLI builds reuse it.
5. **System-wide wired GPU memory pressure**: ML Drift's intermediate tensors are wired
   kernel memory NOT attributed to the process (jetsam shows SAM3 at only 2.57 GB as
   "largestProcess" while the device is out of memory). The entitlement does not help.
   Mitigations that do: more query chunking in attention exports (memattn q_chunks 9→36
   shrinks its score intermediates ~4×; exact) and moving the DETR head to XNNPACK CPU
   (drops the second-largest GPU intermediate pool; fp32-exact).

Measured on the way (iPhone 17 Pro, Metal fp16): vision_tri 4.05–4.2 s, head GPU
0.77–0.92 s, memattn n7 (q36) 4.4 s, maskdec 160 ms, memenc 107–334 ms, initdec 14–29 ms.
